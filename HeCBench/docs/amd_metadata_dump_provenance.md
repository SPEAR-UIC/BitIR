# AMD `sites_metadata.csv` Dump Provenance

This is a provenance-only audit of where AMD/HIP site metadata is generated on `debug-trace`. It does not rerun campaigns or redesign manifests.

## Responsible Code Paths

AMD metadata is generated by `HeCBench/tools/llvm17_inject/build_bench_worklist.py`, not by the runtime trace runner. The path is:

1. `build_bench_worklist.py::build_amd_ir()` emits AMD device LLVM IR text as `device.ll`.
2. `llvm-as device.ll -o device.bc` assembles that IR.
3. `opt -load-pass-plugin libfi_inject.so -passes=fi-inject -fi-site=-1 -fi-dump-sites-rich=... device.bc -o device.dump.bc` walks the IR and writes rich metadata.

Relevant source evidence:

- `build_amd_ir()` constructs the HIP device-only frontend command and writes `device.ll` / `device.bc`: `HeCBench/tools/llvm17_inject/build_bench_worklist.py:121-161`.
- Backend dispatch chooses `build_amd_ir()` when `--backend amd`: `HeCBench/tools/llvm17_inject/build_bench_worklist.py:367-372`.
- Metadata dumping invokes `opt -passes=fi-inject -fi-site=-1 -fi-dump-sites-rich=...` on `ir_bc`: `HeCBench/tools/llvm17_inject/build_bench_worklist.py:385-397`.
- `fi_inject_pass.cpp` assigns `site_id`, `site_class`, opcode, type, source line/column, and `signature_ordinal` while walking the LLVM IR: `HeCBench/tools/llvm17_inject/fi_inject_pass.cpp:176-226`.

## Exact AMD Metadata Command Sequence

The command shape that generates the IR passed to metadata dumping is:

```bash
clang++ \
  -x hip \
  --offload-device-only \
  --offload-arch=${BITIR_MACHINE_HIP_ARCH} \
  --hip-path=${BITIR_MACHINE_RUNTIME_HOME} \
  -Xclang -emit-llvm \
  -S \
  -O0 \
  -g \
  -D__STRICT_ANSI__ \
  -D_GLIBCXX_USE_FLOAT128=0 \
  -I ${source_dir} \
  -I ${repo_root}/HeCBench/src \
  ${src} \
  -o ${out_dir}/device.ll

llvm-as ${out_dir}/device.ll -o ${out_dir}/device.bc

opt \
  -load-pass-plugin ${repo_root}/HeCBench/tools/llvm17_inject/libfi_inject.so \
  -passes=fi-inject \
  -fi-site=-1 \
  -fi-target=${target} \
  -fi-int-float-only=${int_float_only} \
  -fi-include-constants=${include_constants} \
  -fi-dump-sites=${sites_path} \
  -fi-dump-sites-rich=${sites_rich_path} \
  ${out_dir}/device.bc \
  -o ${out_dir}/device.dump.bc
```

The exact input artifact to `opt` is `device.bc`, assembled directly from `device.ll` emitted by the HIP frontend device-only compile.

A representative AMD trace command from the existing v4 artifact confirms the same frontend IR shape used by the AMD execution path:

```bash
/opt/rocm-6.4.2/lib/llvm/bin/clang++ -x hip --offload-device-only --offload-arch=gfx90a --hip-path=/opt/rocm-6.4.2 -Xclang -emit-llvm -S -O0 -g -D__STRICT_ANSI__ -D_GLIBCXX_USE_FLOAT128=0 -I .../HeCBench/src/colorwheel-hip -I .../HeCBench/src .../HeCBench/src/colorwheel-hip/main.cu -o /tmp/.../device.ll
```

For injection execution in `BITIR_AMD_EXECUTION_MODE=injected_ir`, the runner then applies:

```bash
opt -load-pass-plugin libfi_inject.so -passes=fi-inject -fi-site=<site> -fi-bit=<bit> ... device.bc -o device.injected.bc
```

That execution path is in `HeCBench/tools/llvm17_inject/run_benchmark_injection.sh:723-821`.

## Metadata Dump Source Classification

AMD metadata is dumped from LLVM bitcode assembled from HIP frontend-emitted device LLVM IR:

- LLVM IR emitted directly from the HIP frontend: **yes**
- Later canonicalized device IR from an explicit post-frontend `opt` pipeline: **no evidence / unconfirmed**
- Post-optimization IR from an explicit `opt -O*` or named canonicalization pipeline: **no**
- Injected-IR reconstruction path: **no**

The exact file consumed by metadata `fi-inject` dump mode is `device.bc`, not `device.injected.bc`.

## AMD Execution Modes

The new AMD execution-mode switch affects runtime injection execution, not metadata generation:

- `BITIR_AMD_EXECUTION_MODE=injected_ir`: runner injects `device.bc` with `opt` into `device.injected.bc`, lowers, bundles, and links.
- `BITIR_AMD_EXECUTION_MODE=plugin`: runner builds with `clang++ -fpass-plugin=...` for audit comparison.

Metadata generation still comes from `build_bench_worklist.py` and is independent of this execution-mode switch. Therefore the metadata dump point is the same for both runtime modes, because runtime mode is not consulted by `build_bench_worklist.py`.

## Uniformity With NVIDIA

Judgment for whether AMD's current metadata dump point is uniform with NVIDIA's current dump point: **yes**.

NVIDIA and AMD both use `build_bench_worklist.py` to emit backend-specific device LLVM IR at `-O0 -g`, assemble `device.ll` to `device.bc`, and run `opt -passes=fi-inject -fi-site=-1 -fi-dump-sites-rich=...` on `device.bc`.

However, the frontend commands differ:

- NVIDIA: `clang++ -x cuda --cuda-device-only --cuda-gpu-arch=... --cuda-path=... -Xclang -emit-llvm -S -O0 -g ...`
- AMD: `clang++ -x hip --offload-device-only --offload-arch=... --hip-path=... -Xclang -emit-llvm -S -O0 -g ...`

So the AMD dump point is uniform with NVIDIA in the sense that both dump from backend-specific frontend-emitted device LLVM IR before the project's explicit injection pass. This is **not** proof that the IR inventories are semantically identical across machines, because HIP and CUDA frontend/device lowering may expose different instructions, types, operands, ordinals, and result-vs-operand sites before metadata is dumped.

Concise verdict for AMD-vs-NVIDIA dump-point uniformity: **yes**.

Separate inventory-equivalence verdict: **unconfirmed**.
